1. Extract ActionDispatcher from MainViewModel

✓ Implemented
ViewModels/MainViewModel.cs Extensions/IExtra.cs ViewModels/TimerViewModel.cs ViewModels/AiChatViewModel.cs

Problem

MainViewModel's OpenActionResult is a ~100-line switch dispatcher handling timer, AI, shell, settings, URL, web, and generic extras. Each branch marshals data between the action input, sub-ViewModels (Timer, AiChat), and the action panel. This is a shallow module — the interface (one method, two parameters) is nearly as complex as the implementation (seven branches, each setting 4–6 properties on MainViewModel).

Adding a new action requires editing MainViewModel, which already owns search orchestration, scope/category state, clipboard management, settings, and the command palette. The deletion test confirms: if OpenActionResult disappeared, complexity would concentrate in callers — but only because the dispatcher doesn't exist. A real dispatcher behind a seam would let callers stay simple.

Solution

Introduce an IActionDispatcher behind a seam in MainViewModel. Each action type (timer, AI, shell, extras) registers an adapter. The dispatcher receives a SearchResult + input string and returns an ExtraResult, updating the action panel state through a callback rather than by directly setting MainViewModel properties.

MainViewModel's responsibility reduces to: "given a search result, dispatch to the right adapter and surface the result." Tests become possible: each adapter can be unit-tested in isolation, and MainViewModel can be tested with mock dispatchers.

Benefits

  • Locality: Each adapter contains exactly the logic for one action type. Changing the timer UX doesn't touch AI or shell code.
  • Testability: Each adapter is independently unit-testable. MainViewModel can be tested with a mock dispatcher.
  • Leverage: Adding a new action type becomes: implement IActionHandler, register in the dispatcher. No MainViewModel edits.
  • Removes ~80 lines from MainViewModel, moving toward the Single Responsibility Principle.

2. Decouple SettingsViewModel from MainViewModel

Strong
ViewModels/SettingsViewModel.cs ViewModels/MainViewModel.cs Models/SpurConfig.cs Services/ConfigService.cs

Problem

SettingsViewModel holds a direct reference to MainViewModel _main (line 14) and mutates it: _main.Config = _config.Clone() in ~20 property setters. This is a tight coupling — SettingsViewModel cannot exist without MainViewModel, cannot be tested in isolation, and knows the internal structure of its parent.

The config flow is: setting changes → _config.Property = value → _main.Config = _config.Clone() → MainViewModel.OnConfigChanged pushes to services. This makes SettingsViewModel the owner of config propagation — a responsibility that belongs to the config service or a dedicated notifier.

Solution

Replace the MainViewModel reference with an IConfigChangeNotifier interface. SettingsViewModel publishes config changes through this seam. MainViewModel (or the DI container) adapts by subscribing and propagating to services.

Alternatively, make ConfigService observable — raise events when config is saved, and have MainViewModel subscribe directly. This eliminates the SettingsViewModel→MainViewModel hop entirely.

    style SV fill:#fef3c7,stroke:#f59e0b
    style MV fill:#fef3c7,stroke:#f59e0b

After

Benefits

  • Locality: Config propagation logic lives in one place (the notifier/event system), not scattered across 20 property setters.
  • Testability: SettingsViewModel can be tested with a mock IConfigChangeNotifier. No MainViewModel dependency.
  • Seam: The notifier interface creates a real seam — services subscribe independently, and SettingsViewModel doesn't know about them.
  • Eliminates the need for _config.Clone() calls in every setter — the clone was done solely to trigger MainViewModel.OnConfigChanged.

3. Type the IExtra Settings seam

Worth exploring
Extensions/IExtra.cs Extensions/ExtrasRegistry.cs Extensions/Extras/*/*Extra.cs Extensions/Extras/*/*Settings.cs

Problem

The IExtra.Settings property is typed as object?. Every consumer casts: (Settings as KillProcessSettings) ?? new KillProcessSettings(). ExtrasRegistry uses a JSON serialize→deserialize round-trip to bridge between Dictionary<string, JsonElement> (from SpurConfig) and the typed settings POCO. This is fragile — a mismatched type cast fails silently, and the round-trip is wasteful.

The deletion test: if the object? property disappeared, every extra would need its own typed property, exposing the fact that the current interface is too generic. A generic interface would concentrate that complexity.

Solution

Make IExtra generic on its settings type: IExtra<TSettings>. Each extra declares its concrete settings type. ExtrasRegistry uses a non-generic wrapper for storage but exposes typed access. The serialize→deserialize round-trip in LoadSettings/SaveSettings is replaced with direct typed deserialization.

Alternatively, if generics are too invasive, introduce a marker interface IExtraSettings and a typed GetSettings<T>() extension method with cached cast validation.

  • Locality: Cast failures move from runtime to compile time.
  • Eliminates the serialize→deserialize round-trip in ExtrasRegistry (~20 lines of fragile JSON manipulation).
  • Caveat: generics complicate the ExtrasRegistry storage (needs a non-generic wrapper). Worth exploring but requires careful DI design.

4. Split SearchEngineService by result source

Worth exploring
Services/SearchEngineService.cs ViewModels/MainViewModel.cs

Problem

SearchEngineService.SearchAsync is ~180 lines with app matching, file search routing, clipboard browsing, global action building, Windows settings search, URL detection, and web fallback all interleaved in a single method. Each section manages its own result lists, scoring, sorting, and section labeling. The method has low locality — understanding clipboard search requires reading past app and file logic.

The deletion test: if you deleted the clipboard section, would complexity concentrate? No — the clipboard logic is self-contained behind a few lines. But the method structure makes it hard to see that. A split would make each source's independence visible.

Solution

Extract each result source into a separate IResultProvider adapter: AppResultProvider, FileResultProvider, ClipboardResultProvider, ActionResultProvider, WebResultProvider. SearchEngineService becomes an orchestrator that queries each provider and merges results.

Each provider encapsulates its own: enabled-check (config), scoring, result construction, section labeling, and sorting. SearchEngineService only handles ordering sections and applying the web fallback heuristic.

  • Locality: Each provider is self-contained — clipboard logic lives exclusively in ClipboardResultProvider.
  • Testability: Each provider can be unit-tested with mock config and services. Currently SearchEngineService requires all services at once.
  • Seam: Adding a new search source (e.g., browser bookmarks) is a new adapter behind IResultProvider — no SearchEngineService edits.
  • Reduces SearchEngineService from ~360 lines to ~80 lines (orchestration only).

5. Consolidate clipboard ownership

Speculative
ViewModels/ClipboardViewModel.cs ViewModels/MainViewModel.cs Services/ClipboardService.cs Services/SearchEngineService.cs

Problem

Clipboard state is managed across three modules: ClipboardViewModel (history list, copy, delete, pin, selection), MainViewModel (RemoveClipboardItem, ClearClipboard, ActivateClipboardCategory), and SearchEngineService (clipboard-to-SearchResult conversion for search display). The responsibility for "what is a clipboard item and how is it displayed" is split across three files.

When a user deletes a clipboard item from the search results, MainViewModel.RemoveClipboardItem finds the entry by timestamp match (line 1088) — a fragile lookup that duplicates logic already in ClipboardViewModel.Delete (which uses the entry ID directly). This is a leaky seam — clipboard identity leaks from the service (Guid) through the search result (timestamp ticks) into MainViewModel.

Solution

Move all clipboard state management into ClipboardViewModel. MainViewModel delegates RemoveClipboardItem, ClearClipboard, and clipboard category activation to ClipboardViewModel methods. SearchEngineService delegates clipboard-to-SearchResult conversion to a method on ClipboardViewModel or a shared ClipboardResultBuilder.

The SearchResult for clipboard already carries the entry's ClipTimestamp. Add a ClipEntryId (Guid) field to SearchResult so deletion can match by stable ID rather than fragile timestamp comparison.

  • Caveat: requires adding a Guid field to SearchResult for clipboard items. This is a model change but well-scoped.

Top Recommendation

Start with Candidate 1 — Extract ActionDispatcher from MainViewModel.

It has the highest leverage-to-risk ratio: MainViewModel is the project's central nervous system and its action-dispatch logic is the single largest block of coupled code (100 lines of switch branches setting 4–6 properties each). Extracting it into adapters behind an IActionHandler seam:

  • Immediately removes ~80 lines from MainViewModel
  • Creates a natural seam for testing each action in isolation
  • Makes adding new actions a registration, not an edit
  • Doesn't require model changes or DI restructuring — purely an extraction

After that, Candidate 2 (decouple SettingsViewModel) is the logical follow-up — it eliminates the last remaining tight coupling between the two largest ViewModels and enables independent testing of both.
